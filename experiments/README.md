# การทดลอง (Experiments)

การทดลองชุดนี้ใช้ `strace` และโปรแกรมวัดผล เพื่อแสดงว่าฟังก์ชันของ Editor ทำงานผ่าน System Calls และกลไกของ OS อย่างไร และเปรียบเทียบพฤติกรรมการอ่าน/เขียนไฟล์ในกรณีต่าง ๆ

## วิธีรัน

```bash
cd experiments
bash run_all.sh
```

- ใช้เวลาประมาณ 1–2 นาที (ถ้าโปรเจกต์อยู่บน `/mnt/c` การทดลองที่ 1 จะช้ากว่า)
- ผลทั้งหมดอยู่ใน `results/summary.txt` และ trace ละเอียดของแต่ละการทดลองอยู่ใน `results/`
- ต้องมี `gcc`, `make`, `strace`, `python3` (มีใน Ubuntu อยู่แล้ว ยกเว้น strace: `sudo apt install strace`)

## ไฟล์ในโฟลเดอร์นี้

| ไฟล์ | หน้าที่ |
|---|---|
| `run_all.sh` | Build และรันการทดลองทั้งหมด |
| `readbuf.c` | โปรแกรมทดลองที่ 1: อ่านไฟล์ด้วยขนาด buffer ต่าง ๆ |
| `writemode.c` | โปรแกรมทดลองที่ 2: บันทึกไฟล์ด้วยวิธีต่าง ๆ และจำลองการ crash |
| `drive.py` | รัน Editor ใต้ `strace` ใน pseudo-terminal แล้วกดปุ่มอัตโนมัติ (การทดลองที่ 3–5) |

> ผลตัวอย่างด้านล่างมาจากเครื่องทดสอบ Linux (ext4) ใช้เพื่อดูรูปแบบของผลเท่านั้น
> ในรายงานให้ใช้ตัวเลขจาก `results/summary.txt` ที่รันบนเครื่องของตัวเอง

## การทดลองที่ 1: ขนาด Buffer กับการอ่านไฟล์

**วัตถุประสงค์** ศึกษาว่าขนาด buffer ที่ส่งให้ `read()` มีผลต่อจำนวน System Calls และเวลาที่ใช้อย่างไร

**หลักการ** ทุกครั้งที่เรียก `read()` CPU ต้องสลับจาก user mode เข้า kernel mode และกลับออกมา (mode switch) ซึ่งมีต้นทุนคงที่ต่อครั้ง ยิ่งอ่านทีละน้อย ยิ่งต้องเรียกบ่อย

**วิธีทดลอง** อ่านไฟล์ขนาด 1 MB ด้วย buffer 1, 16, 256, 4096, 65536 byte และอ่านทั้งไฟล์ครั้งเดียว (ขนาดจาก `fstat` แบบที่ Editor ใช้ใน `load_fd`) วัดเวลาดีที่สุดจาก 3 รอบ ทำซ้ำ 2 ที่ คือโฟลเดอร์โปรเจกต์ และ `/tmp` เพื่อเปรียบเทียบระบบไฟล์ แล้วยืนยันจำนวนครั้งด้วย `strace -c`

**ผลตัวอย่าง**

| Buffer (byte) | จำนวน `read()` | เวลา (ms) |
|---:|---:|---:|
| 1 | 1,048,577 | 232.89 |
| 16 | 65,537 | 14.51 |
| 256 | 4,097 | 0.95 |
| 4,096 | 257 | 0.08 |
| 65,536 | 17 | 0.04 |
| ทั้งไฟล์ | 2 | 0.09 |

**วิเคราะห์**
- จำนวน `read()` = ขนาดไฟล์ ÷ ขนาด buffer + 1 (ครั้งสุดท้ายคืน 0 = จบไฟล์) ตรงกับที่ `strace -c` นับได้
- เวลาแปรผันตามจำนวน System Calls เกือบตรง ๆ buffer 1 byte ช้ากว่า 4096 byte หลายพันเท่า ทั้งที่อ่านข้อมูลเท่ากัน แสดงว่าต้นทุนหลักคือการเข้า–ออก kernel ไม่ใช่ปริมาณข้อมูล
- หลัง 4096 byte (ขนาด page) เวลาแทบไม่ลดลงอีก
- Editor อ่านทั้งไฟล์ด้วย `read`/`pread` ไม่กี่ครั้งหลังถามขนาดจาก `fstat` จึงเป็นวิธีที่เหมาะสม
- ถ้ารันโปรเจกต์บน `/mnt/c` (ระบบไฟล์ของ Windows ผ่าน WSL) จะเห็นว่าช้ากว่า `/tmp` (ext4) ชัดเจน เพราะทุก System Call ต้องส่งต่อไปยัง Windows

## การทดลองที่ 2: วิธีบันทึกไฟล์ และความปลอดภัยเมื่อโปรแกรม crash

**วัตถุประสงค์** เปรียบเทียบ System Calls เวลา และความปลอดภัยของข้อมูล ระหว่างวิธีบันทึกไฟล์ 4 แบบ

| วิธี | ขั้นตอน |
|---|---|
| `direct` | `open(O_TRUNC)` → `write` → `close` (วิธีเดิมของ Editor รุ่นแรก) |
| `small` | เหมือน direct แต่ `write` ทีละ 64 byte |
| `direct_fsync` | direct + `fsync` |
| `safe` | เขียนไฟล์ `.tmp` → `fsync` → `rename` ทับไฟล์จริง (วิธีที่ Editor ใช้ปัจจุบัน) |

**หลักการ**
- `write()` เพียงคัดลอกข้อมูลเข้า page cache ใน memory ของ kernel ยังไม่ลง disk ทันที
- `fsync()` บังคับให้ kernel เขียนข้อมูลลง disk จริงและรอจนเสร็จ
- `rename()` เป็น atomic operation ในระบบไฟล์เดียวกัน คือเกิดขึ้นทั้งหมดหรือไม่เกิดเลย

**วิธีทดลอง** บันทึกไฟล์ 100 KB วิธีละ 50 ครั้ง วัดเวลาเฉลี่ย นับ System Calls ต่อ 1 ครั้งด้วย strace แล้วทดสอบ crash: ไฟล์เดิมเป็นตัว `A` 100 KB บันทึกเนื้อหาใหม่ (`B`) แล้วฆ่า process ตัวเองด้วย `SIGKILL` ตอนเขียนได้ครึ่งเดียว

**ผลตัวอย่าง**

| วิธี | System Calls ต่อ 1 ครั้ง | เวลาเฉลี่ย (ms) |
|---|---|---:|
| `direct` | openat 1, write 1, close 1 | 0.069 |
| `small` | openat 1, write 1600, close 1 | 0.613 |
| `direct_fsync` | openat 1, write 1, fsync 1, close 1 | 0.219 |
| `safe` | openat 1, write 1, fsync 1, close 1, rename 1 | 0.253 |

| Crash test | ขนาดไฟล์หลัง crash | ผล |
|---|---:|---|
| `direct_crash` | 51,200 byte, เป็นตัว `B` | ข้อมูลเก่าหาย ข้อมูลใหม่ได้ครึ่งเดียว |
| `safe_crash` | 102,400 byte, เป็นตัว `A` | ไฟล์เดิมสมบูรณ์ |

**วิเคราะห์**
- `small` เรียก `write` มากกว่า 1600 เท่า จึงช้ากว่าชัดเจน สอดคล้องกับการทดลองที่ 1 Editor จึงรวมข้อความทั้งไฟล์เป็นก้อนเดียว (`build_text`) แล้ว `write` ครั้งเดียว
- `fsync` เพิ่มเวลามากที่สุดในขั้นตอนทั้งหมด เพราะต้องรอ disk จริง แต่จำเป็นเพื่อให้ข้อมูลไม่หายเมื่อไฟดับ
- `safe` ช้ากว่า `direct` เล็กน้อย แต่เป็นวิธีเดียวที่ไฟล์เดิมไม่เสียหายเมื่อ crash เพราะ `O_TRUNC` ของ direct ลบข้อมูลเก่าทิ้งก่อนเขียนของใหม่ ส่วน safe เขียนลงไฟล์อื่นก่อน แล้วใช้ `rename` ที่เป็น atomic สลับไฟล์
- ข้อแลกเปลี่ยน: ยอมเสียเวลาเพิ่มระดับไม่ถึง 1 ms ต่อการบันทึก เพื่อความถูกต้องของข้อมูล

## การทดลองที่ 3: การวาดหน้าจอ

**วัตถุประสงค์** เปรียบเทียบจำนวน `write()` เมื่อวาดหน้าจอแบบรวมทั้งเฟรมแล้วเขียนครั้งเดียว กับการเขียนทีละชิ้น

**วิธีทดลอง** Compile Editor อีกรุ่นด้วย `-DSLOW_RENDER` (ใน `render.c` ฟังก์ชัน `ob_add` จะเรียก `write` ทันทีทุกชิ้นแทนการเก็บเข้า buffer) เปิดไฟล์ 300 บรรทัด กดลูกศรลง 20 ครั้ง นับ `write` ด้วย `strace -c`

**ผลตัวอย่าง**

| รุ่น | `write()` ทั้งหมด | ต่อการกด 1 ครั้ง |
|---|---:|---:|
| รวมเป็นก้อนเดียว (ปกติ) | 23 | ~1 |
| เขียนทีละชิ้น (`SLOW_RENDER`) | 2,153 | ~102 |

**วิเคราะห์**
- รุ่นปกติใช้ 1 `write` ต่อ 1 เฟรม (23 = เฟรมแรก + 20 ครั้งที่กด + เข้า/ออกหน้าจอสำรอง)
- รุ่นทีละชิ้นใช้ราว 100 ครั้งต่อเฟรม (ประมาณ 2 ครั้งต่อบรรทัดบนจอ) ต่างกันเกือบ 100 เท่า
- นอกจากเรื่องต้นทุน System Call แล้ว การเขียนทีละชิ้นยังทำให้ terminal แสดงผลระหว่างวาดไม่เสร็จ ผู้ใช้เห็นจอกะพริบ

## การทดลองที่ 4: Canonical mode กับ Raw mode

**วัตถุประสงค์** แสดงผลของการตั้งค่า `termios` ต่อการทำงานของ `read()`

**วิธีทดลอง** พิมพ์ `hello` แล้วกด Enter ให้ `cat` (terminal โหมดปกติ) และให้ Editor (raw mode) ดูค่าที่ `read(0, ...)` คืนมาด้วย `strace -e trace=read` และปล่อย Editor ว่างไว้ 2 วินาที

**ผลตัวอย่าง**

| โปรแกรม | `read()` ที่ได้ข้อมูล | สิ่งที่ได้ต่อครั้ง | `read()` ที่คืน 0 |
|---|---:|---|---:|
| `cat` (canonical) | 1 | `"hello\n"` 6 byte ครั้งเดียว | 1 (Ctrl+D) |
| Editor (raw) | 8 | ทีละ 1 byte: `h`, `e`, `l`, `l`, `o`, `\r`, Ctrl+Q ×2 | 38 |

**วิเคราะห์**
- โหมดปกติ tty driver ใน kernel เก็บตัวอักษรไว้ จัดการ Backspace และ echo เอง แล้วส่งให้โปรแกรมทีเดียวเมื่อกด Enter
- Raw mode (ปิด `ICANON`, `ECHO`) kernel ส่งทุกปุ่มทันที Editor จึงตอบสนองลูกศรและปุ่มลัดได้ แต่ต้องวาดตัวอักษรเอง
- Enter มาเป็น `\r` ไม่ใช่ `\n` เพราะปิด `ICRNL`
- `read()` ที่คืน 0 ประมาณ 10 ครั้งต่อวินาที มาจาก `VMIN=0, VTIME=1` ทำให้ `read` กลับมาทุก 0.1 วินาทีแม้ไม่มีปุ่ม นี่คือข้อแลกเปลี่ยนที่ตั้งใจ เพื่อให้ลูปหลักได้ตรวจธงจาก Signal (resize, auto-save) แม้ผู้ใช้ไม่กดอะไร

## การทดลองที่ 5: Run command (Process และ IPC)

**วัตถุประสงค์** แสดงลำดับ System Calls เมื่อ Editor สร้าง process ลูกเพื่อรันคำสั่ง

**วิธีทดลอง** กด Ctrl+R รัน `echo hello from child` ใต้ `strace -f` (ติดตาม process ลูกด้วย)

**ผลตัวอย่าง** (ตัวเลขหน้าบรรทัดคือ PID)

```
870  pipe2([4, 5], 0)                          = 0      แม่สร้างท่อ
870  clone(... SIGCHLD ...)                    = 871    fork สร้างลูก
871  dup2(6, 0) / dup2(5, 1) / dup2(5, 2)               ลูกต่อ stdin=/dev/null, stdout/stderr=ท่อ
871  execve("/usr/bin/sh", ["sh", "-c", "echo hello from child"]) = 0
871  exit_group(0)                                      ลูกจบ
870  --- SIGCHLD ---                                    kernel แจ้งแม่ว่าลูกจบ
870  wait4(871, [WEXITSTATUS == 0]) = 871               แม่เก็บสถานะ ลูกไม่เป็น zombie
```

**วิเคราะห์**
- `fork()` ใน glibc ถูกแปลงเป็น System Call `clone` จริง
- process ลูกคือตัวที่เรียก `dup2` และ `execve` process แม่ไม่ถูกแทนที่ Editor จึงทำงานต่อได้
- `execvp` ค้นหา `sh` ตาม `PATH` จะเห็น `execve` ที่คืน `ENOENT` หลายครั้งก่อนเจอ `/usr/bin/sh`
- เมื่อลูกจบ kernel ส่ง `SIGCHLD` ให้แม่ และ `wait4` เก็บ exit code ถ้าไม่เรียก ลูกจะค้างเป็น zombie
- Output ของลูกเดินทางผ่าน `pipe` กลับมาให้แม่อ่าน เป็นการสื่อสารระหว่าง process (IPC)

## ภาพรวม: System Calls ในการใช้งานจริง

`results/overall.txt` คือ `strace -c` ของการเปิดไฟล์ พิมพ์ 3 ตัวอักษร Enter บันทึก และออก แสดงทุก System Call ที่ Editor เรียก เช่น `ioctl` (termios, ขนาดจอ), `read`/`write`, `openat`, `pread64`, `flock`, `alarm`, `rt_sigaction`, `fsync`, `rename`, `unlink` ใช้เป็นตารางสรุปในรายงานได้
